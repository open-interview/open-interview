## Hook — It starts quietly, then the dashboard turns red

It starts quietly. A query that used to answer in 400 milliseconds now takes 1.4 seconds. A week later it is 6 seconds, your on-call rotation feels like a carousel, and then the question lands: "You have a PostgreSQL table with 100M rows partitioned by date. A query filtering on a specific date range is still slow. What would you check in the EXPLAIN plan, and how would you optimize it?" Here is the plot twist most developers discover far too late: partitioning alone never guarantees speed. In fact, a partitioned table can be *slower* than a modest heap table when the parts are fighting against you [7]. The real question isn't whether you added PARTITION BY RANGE — it's whether PostgreSQL is actually using the architecture you handed it. That single misunderstanding is what turns a routine query tuning session into a full-blown incident.

## Problem — 100M rows, a date filter, and a plan that ignores your effort

On paper, date partitioning is a beautiful promise: queries for a specific time window scan a handful of partitions instead of the entire table [3]. In reality, a slow query on a partitioned table is a whodunit with four prime suspects. First, partition pruning might silently fail — a WHERE clause wrapped in date_trunc() or a type cast can prevent PostgreSQL from eliminating partitions, and suddenly your elegant design scans every single partition [3]. Second, the planner might pick a sequential scan over an index because the table is bloated, statistics are stale, or the index simply doesn't cover the query. Third, watch for an expensive Sort or HashAggregate node — a query that fetches the right rows but then sorts millions of them is a query that says 'I have a memory problem,' not an indexing problem [2]. Finally, the partition key itself might not match how your users actually query. Sound like a lot to juggle? That is precisely why the EXPLAIN output is the only trustworthy witness; guessing without it is how 'small optimizations' become 3am rollbacks.

## Real-World Case — Cloudflare's 1,616 GB table and the two-minute heartbeat

Cloudflare's DEX product ingested device experience logs from customers whose fleets reported in constantly — 30,000+ devices per large customer, every two minutes, totaling about 1,000 inserts per second [1]. The data lived in a single plain PostgreSQL table, and as adoption grew, seven-day dashboard time-range queries fell apart: chart renders took several seconds and timeouts climbed [1]. The fix was not a bigger machine. It was a disciplined diagnosis of partitioning and query planning — pruning, index utilization, and pre-aggregation — that delivered 5x to 35x faster queries on 500M to 1B row datasets depending on the time window [1]. After pre-aggregation, charts rendered instantly, hitting up to 1,000x speedup [1]. The storage bill collapsed from 1,616 GB to 49 GB — a 33x compression that let them retain 33x more history for the same cost [1]. Read those numbers twice. This is what happens when a team stops throwing hardware at a query problem and starts reading what PostgreSQL is actually telling them.

## Deep Dive — Reading the evidence: pruning, indexes, sorts, and the cluster decision

Every performance investigation starts the same way: EXPLAIN (ANALYZE, BUFFERS) is the interrogation room and the plan is the confession [2]. The first detail to verify is partition pruning. A healthy plan shows only a few partitions scanned for a narrow date range; a plan that lists dozens means the planner could not prune, and you have to scrub the predicate of function calls and casts [3]. Secondly, look at access method: an Index Scan where a Seq Scan appeared means the planner re-evaluated its assumptions — often because your composite index was built in the wrong column order. The rule of thumb holds: lead with equality columns, then range columns, because a composite index on (date, status) serves date-range filters, while (status, date) frequently ends up nearly useless [4]. Third, hunt for Sort and HashAggregate nodes. A sort that spills to disk is a warning that the planner's memory estimate was optimistic — the fix is often an index that already matches the ORDER BY, or pre-aggregation further up the pipeline [2]. Last, the CLUSTER card: reordering physical rows to match an index can drastically shrink range scans, but it locks the table, so it belongs in a maintenance window, not at the peak of traffic [5]. The counterintuitive insight here: the fastest query plan is usually not the index you add — it's the one you remove. Fewer rows touched beats fancier indexing every time.

## Workflow — The five-step diagnosis pipeline that ends the guessing

Building on the deep dive, here is a repeatable pipeline for your next slow date-range query. Step one: capture a baseline with EXPLAIN (ANALYZE, BUFFERS) so later changes have something to beat [9]. Step two: confirm pruning — count the partitions actually scanned [3]. Step three: verify index utilization; if a Seq Scan persists, look at the index's column order [4]. Step four: inspect Sort and aggregate nodes for spills [2]. Step five: decide whether CLUSTER or pre-aggregation is the right structural move, and monitor with pg_stat_statements so the next slow query finds you before your users do [8]. ## Lessons Learned — What Cloudflare's 33x story taught you (and the battle scars along the way)

The takeaways here are deceptively simple and brutally expensive to learn the hard way. Partition pruning is the first suspect, always — an unpruned partitioned query reads data you already decided you did not need [3]. Second, composite index column order is a silent multiplier: (filter_column, date) vs (date, filter_column) can be the difference between an instant answer and a disk-heavy sort [4]. Third, CLUSTER is a superpower with a lockdown cost — beautiful for range scans in a maintenance window, dangerous in a live firefight [5]. Fourth, staring at one EXPLAIN plan and declaring victory is a classic battle scar; long-term observability through pg_stat_statements is what catches the *next* regression [8]. And the biggest plot twist of all: sometimes the answer is not a better index but pre-aggregation — Cloudflare's 1,000x charts came after summarization, not after a cleverer B-tree [1]. If this feels overwhelming, you are not alone; every senior engineer on your team has a story about a query that was 'fixed' twice before it was actually fixed. The question is whether your *next* hour goes to debugging or to a tool that tells you the truth.

## Conclusion

Cloudflare's real win was never the hardware — it was learning to let PostgreSQL tell them the truth, then acting on it: prune, index with intent, sort less, and occasionally cluster [1]. Tomorrow morning, before you add another index, run EXPLAIN (ANALYZE, BUFFERS) on your slowest partitioned query and ask the four questions: Is pruning working? Is an index actually used? Is there a Sort or HashAggregate hiding the truth? Is the partition key aligned with how users query? Do that on every slow query, and the interview answer stops being a rehearsed list — it becomes the way you debug. One memorable insight to share with your team: the fastest query plan is often not the index you *add*; it's the partitions you never read.
