## Hook — The alert that changed how engineers think about indexes

Picture this: it is 2am, and the monitoring dashboard is glowing red. The Apdex score is sliding during every API traffic spike, IOPS are breathing down the neck of a 24K limit, and a query you assumed was fine is taking more than 30 seconds on average. This was reality for the team at CoinGecko, one of the most-trafficked crypto price data aggregators on the internet [1]. They had done the 'responsible' thing — partitioned a massive table by date, added indexes, followed the playbooks. And the database still bent under load. The stakes could not be higher: every additional millisecond of p99 latency is a customer refreshing their dashboard, another API slot burning, another support ticket. What do you check when the obvious solutions have already been applied? The answer starts in a place most developers only visit when things are broken: the EXPLAIN plan.

## Problem — Why a 100M-row, date-partitioned table is still slow

Now take the interview scenario that triggers a thousand resumes: a PostgreSQL table with 100 million rows partitioned by date, and a query filtering on a specific date range that is still slow. On the surface, this should be solved already — partitioning exists precisely so the database reads only the slices it needs [2]. Yet there you are, staring at latency that refuses to budge. In practice, 'slow' is almost never one bug. It is a stack of small betrayals: the partition pruning that silently stopped working when a query boundary shifted, the index the planner decided was not worth the seek cost, the sort operation running in memory and spilling to disk. Many developers discover the hard way that partitioning is permission to be fast, not a guarantee of speed. Consequently, the real diagnostic loop has three suspects: first, is the planner actually pruning partitions? Second, is your index being used, or is it doing a full sequential scan? Third, is an expensive sort or hash aggregate eating the savings? What if the fix for one problem makes another query measurably worse — is that a cost you are willing to pay? For CoinGecko, the answer to that last question was the decisive one.

## Real-World Case — CoinGecko: 24K IOPS, 4 seconds of p99, and one very loud table

CoinGecko's table told the whole story in numbers: 1TB+ of data, 8+ years of hourly price snapshots, average queries breaking 30 seconds, and IOPS that kept breaching their 24K limit, setting off alarms on the daily [1]. The team's solution was declarative partitioning, composite indexes, and — critically — verifying partition pruning in the EXPLAIN plan rather than assuming it worked. The results are the kind of before/after you paste into a slide deck: p99 response time dropped 86%, from 4.13 seconds to 578 milliseconds. IOPS dropped 20% — a win that multiplied across every read replica in the fleet. Individual queries got 6 to 8 times faster [1]. But the story would not be worth telling without its twist: one query, the one without an upper date bound, performed worse after partitioning. It scanned every partition — including the empty future ones the team had already created. That single regression is the most valuable lesson in the entire incident: pruning must be verified in EXPLAIN, not trusted. The tool that saved everything almost broke one thing nobody expected. [1]

## Deep Dive — Pruning, index scans, and the physics of a WHERE clause

This leads to the core mechanics. When a query touches a partitioned table, the planner evaluates every partition's constraints and eliminates the ones that cannot contain matching rows — a process called partition pruning [2]. If pruning works, an EXPLAIN on a January range touches only January's data. If it fails, the Append node shows every partition in the plan, including the empty ones, and you just scanned five years of history to answer a question about one month. That is precisely what happened to CoinGecko's unbounded query: no upper bound meant the planner could not eliminate future partitions, so it scanned them all [1]. The second lever is index utilization. The planner is a cost accountant — it compares a sequential scan against an index scan and picks what it believes is cheaper [3]. A low-selectivity filter, stale statistics, or a composite index with its columns in the wrong order all push it toward scanning. Finally, there is sorting. ORDER BY and GROUP BY on an unindexed or misindexed column trigger explicit sorts and hash aggregates that can dominate the entire query cost, nullifying the savings from pruning. The fix pattern that emerges: composite indexes on (date, filtered_columns) that cover the WHERE clause [4], and clustering to physically order rows to match the index, reducing read amplification [5]. ## Workflow — The 7-step triage that turns a slow partition into a fast one

Building on the mechanics, the fix is a repeatable workflow rather than a single command. Start with EXPLAIN ANALYZE with BUFFERS enabled to see the true plan and buffer cost [3]. Check whether the Append node lists one partition or fifty. Then check the scan method: seq scan means the index is being ignored; index scan means pruning saved you; either way, look for the words 'Sort' or 'HashAggregate' and flag them as suspects. If pruning is failing, revisit the query boundary — the missing upper date bound in CoinGecko's case — because no index can rescue a query that reads every partition [1]. Then create the composite index concurrently so the table stays live, and optionally CLUSTER the table to align physical row order with the index, remembering that CLUSTER rewrites the table and requires downtime consideration [5]. Refresh statistics with ANALYZE, then re-run EXPLAIN and compare: partition count, scan type, buffer reads, and total cost. Iterate until the numbers move in your direction. ## Code Example — EXPLAIN, index, cluster, repeat: the commands that saved a 1TB table

Now for the concrete steps, all runnable against a real date-partitioned events table. Each command corresponds to one stage of the workflow: diagnose, index, cluster, re-verify. Run step one in every environment before touching anything — the plan tells you whether pruning is already working, and without that baseline, every subsequent change is guesswork. The composite index in step two covers both the partition filter and the status filter, giving the planner a single structure to serve the whole WHERE clause [4]. Step three, CLUSTER, is the read-amplification fix: it physically rewrites rows in index order so range scans touch contiguous pages [5]. Finally, re-running EXPLAIN after ANALYZE confirms whether the plan changed — and whether the query that lacks an upper bound quietly regressed, exactly as it did for CoinGecko [1].

## Lessons Learned — Verify pruning, then index, then measure

So what stays with you after this journey? Three things. First, partitioning is a promise the planner must keep — and you can only confirm it with EXPLAIN. CoinGecko's regression proves that 'obvious' optimizations can ship in the wrong direction when verification is skipped [1]. Second, the order of operations matters: diagnose before you alter, index for the actual WHERE clause, cluster for the read pattern, and always re-measure. Third, watch your unbounded queries specifically — anything without an upper date bound is a prime candidate for scanning every partition, including the empty future ones. Battle scar to share with your team: run the EXPLAIN after every schema change, not just before it. Treat a query that got slower as a feature request to understand the planner, not a bug to hide behind an index. And remember — p99 of 578ms was not achieved by adding more hardware; it was achieved by reading fewer bytes [1]. The next time your slow query fires an alert, you will know exactly what to check first.

## Conclusion

The moral of this story is deceptively simple: read fewer bytes. CoinGecko did not achieve a 86% drop in p99 latency — down to 578ms — by throwing hardware at the problem, but by making sure the database only touched the partitions and rows it actually needed [1]. The real takeaway for tomorrow: treat EXPLAIN as a required step, not a debugging afterthought. Run it before every optimization, and after every schema change. And when a query gets slower instead of faster, do not fight the planner — listen to what it is telling you about your data. Share one sentence with your team the next time a slow query page fires: partitioning is only as fast as the plan it produces, and the plan is only as good as the proof you verify.
