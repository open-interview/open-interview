Picture this: a single tab component used across hundreds of UK government services, where accessibility isn't a nice-to-have—it's the law [1]. When a developer proposed stripping out the JavaScript and driving tabs purely with radio inputs and CSS `:checked`, GOV.UK's design team faced a public debate that reveals everything about how the most important websites in a country are actually built. This is the story of that trade-off, and the lessons it holds for every frontend developer who reaches for a JavaScript library before considering what CSS can already do.

## Hook — What if your tabs were the law?

Here is a scenario that might keep you up at night. Your component ships to thousands of pages. People who cannot use a mouse rely on it daily. And if it breaks for them, you are not just facing an angry bug report—you are facing legal liability. That is the daily reality for the team behind GOV.UK's design system, which maintains the tabs component powering services across the UK government [1]. The stakes are so high that the public discussion about how these tabs should work is preserved forever in GitHub, open for anyone to read. Sound like a lot of pressure for a UI that most developers would build with a weekend of React? It is. And the debate that unfolded over a seemingly simple question exposes how much craft hides inside what looks like a trivial component.

## Problem — The JavaScript reflex, and the debt it hides

Many developers reach for a tab library the moment a design calls for one. npm install, import a component, sprinkle in some onClick handlers, done. But here is the thing no one tells you about that reflex: every line of JavaScript is a line that can fail. A dropped network request, a bundle that fails to parse, a script blocked by an aggressive ad-blocker, a screen reader that chokes on dynamically-injected DOM. Now multiply that fragility by three hundred services, and the cost isn't a slow page—it's a citizen unable to renew a passport, file a tax return, or access a driving licence. The core problem this story tackles is deceptively simple: how do you build an interactive component that keeps working even when JavaScript never arrives? The answer, as the GOV.UK team knew, starts with questioning whether you need JavaScript at all. This isn't about hating modern tooling—it's about knowing when the foundation can carry the weight without it.

## Real-World Case — GOV.UK's public reckoning on tabs

The GOV.UK Design System maintains its tabs component with accessibility as a non-negotiable requirement under the Equality Act 2010 and WCAG 2.2 AA [1]. A developer on a live service proposed the exact technique you are about to learn: replacing the JavaScript-backed tabs widget with pure-CSS radio inputs driving panel visibility through `:checked`. The proposal was logged against the GOV.UK design system backlog for the team to adopt. Here is the plot twist: the radio-hack was deliberately never shipped. The debate is preserved publicly in issue #100 of the Govuk Design System backlog [1]. Why does that matter? Because the refusal to ship was itself a design decision. The team weighed the elegance of the CSS-only approach against the quirks of radio semantics, keyboard expectations, and screen-reader behavior—and chose the path that kept the component keyboard-operable and screen-reader-safe across hundreds of live services. The takeaway is not that CSS-only tabs are wrong. The takeaway is that every component decision at this scale is a public, high-stakes debate over who might be excluded—and getting it right matters more than shipping something clever.

## Deep Dive — The CSS machinery under the hood

Now let's pull back the curtain on the technique itself, because the GOV.UK team's caution doesn't mean the pattern is useless—it means you must understand its boundaries before adopting it. The pattern rests on three pillars of CSS that many developers underuse. First, the radio group: multiple `` elements sharing one `name` attribute behave like a toggle, because selecting one unchecks the others. That gives you exclusive state with zero JavaScript. Second, the sibling selector: using `.tabs input:not(:checked) ~ .panel` lets you hide every panel except the one controlled by the checked radio. Third, the label connection: each `` makes the tab clickable and keyboard-focusable. Accessibility enters here, and this is where it gets nuanced. Radios have their own keyboard behaviour—arrow keys move between options—which can feel odd for tabs. That is precisely why the GOV.UK team hesitated. Yet the pattern still shines in specific contexts: a design-system documentation page, an internal tool, anywhere that progressive enhancement is a hard requirement. The line, halved by grid's `repeat(2, 1fr)` on desktop and `1fr` on mobile, is the responsive heart of it. And the `prefers-reduced-motion` guard means your entrance animations disappear for users who ask for them to [2][3].

## Workflow — From wireframe to resilient tabs in five steps

Building on the mechanics, here is the mental model to follow. The workflow is less about typing code and more about making deliberate, sequenced decisions—each one feeding the next. Step one: decide the semantics that matter, because the entire pattern hinges on using radio inputs as your source of truth. Step two: wire up the labels so each tab is reachable by keyboard and has a screen-reader-visible label. Step three: write the CSS that reveals and hides panels elegantly using sibling selectors, keeping the markup declarative. Step four: lay out responsive cards so the same content composes to a 2×2 grid on desktop and a single column on mobile without media-query gymnastics. Step five: add polish—staggered entrance animations wrapped in a motion-safe media query and focus-visible outlines so keyboard users always know where they are. ## Code Example — Building the resilient tab panel

Let's make all of that concrete. Building on the workflow, here is the full pattern in HTML and CSS. Notice how the markup is pure semantic structure—radios, labels, sections, and articles—with not a single `` tag in sight. The radio carries the checked state, the label is what humans interact with, and each section becomes a panel whose visibility is governed entirely by CSS. The magic line is `.tabs input:not(:checked) ~ .panel { display: none; }`—it hides every panel except the one whose radio is checked. Meanwhile, the grid handles the responsive layout, and the `prefers-reduced-motion` query scopes the staggered fade-in only to users who haven't opted out of motion. For keyboard users, the radio inherits native focus behavior, and the global `:focus-visible` outline makes the focused element unmistakable. This is the essence of progressive enhancement: the content and its interactivity exist in plain HTML, and CSS merely layers on the experience.

## Lessons Learned — What the GOV.UK debate teaches every developer

So what should you take away from a debate that was, in the end, deliberately never merged? First, the pattern is genuinely valuable—CSS-only toggles, carousels, and accordions are legitimate tools in the right context, and knowing them makes you a stronger engineer. But second, and more important, is the discipline the GOV.UK team modelled: before shipping clever, ask who might be excluded. The rule of thumb is simple. Use pure-CSS interactivity when JavaScript delivery cannot be guaranteed, when you need a bulletproof progressive-enhancement floor, or when the semantics of the pattern genuinely match the component's meaning. Reach for full JavaScript widgets when you need complex keyboard interactions, dynamic content, or behaviour the native element cannot express. The real takeaway is the workflow itself: build the semantic HTML first, let CSS layer the enhancement, and treat accessibility as the contract you sign, not a feature you bolt on later. Your future self—and your users—will thank you.

## Conclusion

The next time you reach for a JavaScript tab library, pause and ask one question: could CSS carry this weight? The GOV.UK team showed that even at the scale of a national government, the answer is often yes—and that the real craft lies not in shipping clever hacks, but in choosing what to ship and what to leave behind [1]. Start small: build one component today with pure CSS interactivity, run it through a keyboard and a screen reader, and watch how much of your JavaScript you didn't actually need. Share the insight with your team—the quiet superpower is knowing when the platform already has the answer.
