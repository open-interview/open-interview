## Hook — The query was supposed to be fast. It wasn't.

You partitioned a 100M-row table by date. You bragged about it in the standup. The dashboard still crawls. Sound familiar? Among the most frustrating situations in database work is the moment you realize the elegant architecture you shipped is doing nothing for the query that actually matters. A date-range filter that should touch a single month is somehow touching everything. The plan looks enormous. The disk is thrashing. And the paging channel is starting to fill with messages like "Is the DB down?" Every one of these symptoms traces back to a breakdown on the journey between your SQL and the storage engine - a breakdown that EXPLAIN can expose in seconds once you know what to look for. The stakes are genuinely high: on a table with hundreds of partitions, a single failed pruning decision can turn a query that should take milliseconds into one that takes minutes. Partitioning is not a silver bullet; it is a contract you sign with the planner, and the planner collects payment from you every time you write a WHERE clause [2].

## Problem — Partitioning is a contract, and your WHERE clause is the signature

Here is the plot twist: partitioning does not make queries fast on its own. It only removes data from consideration when the planner or executor can prove a partition cannot contain matching rows. Without that proof, the query scans everything and partitioning becomes pure overhead - more planning time, more locks, more metadata in memory [2]. The pain point affects anyone running analytics on time-series data: events, orders, metrics, webhooks. Three failure modes dominate. First, partition pruning fails because the predicate wraps the partition key in a function like date_trunc('month', event_date) = '2024-01-01' - the planner cannot compare a function result against partition bounds, so nothing gets eliminated [3]. Second, pruning succeeds but the surviving partition is still huge, and the planner chooses a sequential scan because the index either does not exist or does not cover the extra filters like status = 'completed'. Third, the partition key itself is wrong for the workload - for example partitioning by account ID when every query filters on time - so no query ever aligns with the scheme [2]. Each failure looks different in the plan, which is why the first skill to build is reading the evidence before touching the tuning knobs. The good news? Every one of these failures shows up as a fingerprint in EXPLAIN output.

## Real-World Case — ChartMogul: when partitioning becomes the incident

ChartMogul's ingestion database is a cautionary tale about every partitioning mistake compounding at once. Their core database processed millions of webhooks daily, partitioned with LIST partitioning - one partition per account. It felt tidy at first, but as the company grew, hundreds or thousands of partitions made the scheme unsustainable [1]. The symptoms read like a database horror story: extreme read IOPS from queries chewing through hundreds of thousands or millions of records, out-of-memory crashes from large and inefficient indexes, stale statistics that demanded constant vacuuming, and administrative operations that took ACCESS EXCLUSIVE locks on the parent table [1]. Their single RDS instance became a single point of failure and the most expensive instance in their AWS bill [1]. In late 2022 the team decided to migrate, swapping LIST for HASH partitioning with 30 partitions per large table - roughly 2.5GB each - and moved the data to their sharded platform database [1]. The payoff was dramatic: a 5x improvement in simple SELECT queries, a 3x improvement for SELECTs with joins, a 10% reduction in AWS RDS costs by eliminating the most expensive instance and its replica, and 5,000 lines of legacy code deleted [1]. Most importantly, all data normalization incidents vanished from April 2023 onward [1]. The uncomfortable lesson here is that 'partitioned' and 'optimized' are not synonyms - and that the number of partitions is a design decision with real, measurable consequences at scale [2].

## Deep Dive — Reading the fingerprints: pruning, indexes, and the expensive sort

Now the detective work. When a query on a partitioned table is slow, your instinct might be to add indexes or buy a bigger instance. Resist it. The correct first move is always EXPLAIN (ANALYZE, BUFFERS), because every wrong turn leaves a fingerprint in the plan. 💡 Insight: Partition pruning comes in two flavors. Plan-time pruning removes partitions before execution when the WHERE clause uses constants, and pruned partitions simply never appear as children in the plan. Execution-time pruning handles parameters and values from subqueries or join parameters, keeping all subplans in the plan but reporting them with (never executed) or a lower loops count [1,2]. 🔥 Hot Take: A plan that shows one Append child is not necessarily pruning better than one that lists ten - if the ten reflect runtime pruning on a parameterized query, the executor is doing the right work at the right time [2]. The telltale line to hunt for is Subplans Removed: N in EXPLAIN ANALYZE output; if N is missing and every child scan reports actual rows, every partition was read [3]. Next, check index utilization: a large surviving partition scanned sequentially means your composite index does not match the filter shape. The fix is usually a composite index on (partition_key, filtered_columns) so the index condition covers the whole WHERE clause [4]. Finally, watch for expensive Sort nodes or hash aggregates on top - these are often the hidden cost that makes a correctly-pruned query feel slow. ⚠️ Watch Out: PostgreSQL's planner handles up to a few thousand partitions fairly well only if typical queries prune down to a handful; planning time and session memory grow as more partitions remain after pruning, one reason ChartMogul's hundreds of LIST partitions hurt them [1,2].

## Workflow — A disciplined five-step diagnosis before you touch a single knob

Building on the deep dive, teams benefit from a repeatable diagnosis workflow instead of whack-a-mole tuning. The journey from slow query to fast plan looks like this: 1) Reproduce the slow query and capture EXPLAIN (ANALYZE, BUFFERS) as a baseline. 2) Verify partition pruning by counting Append children and looking for Subplans Removed. 3) Check the access method inside each surviving partition - index scan or sequential scan - and compare against your filters. 4) Audit the top nodes for expensive sorts or hash aggregates that rewrite the query's shape. 5) If all else fails, question the partition key itself and simulate the workload before re-partitioning. ## Lessons Learned — The three battle scars every team carries

After the journey, the takeaways crystallize into three scars teams keep re-opening until they learn them. First, battle scar one: believing EXPLAIN without ANALYZE. Runtime pruning cannot be observed without execution, so a plan full of children and no Subplans Removed line means nothing was pruned - always pair plain EXPLAIN with EXPLAIN (ANALYZE, BUFFERS) [2,3]. Second, battle scar two: wrapping the partition key in a function or cast. A predicate like event_date::date = CURRENT_DATE defeats pruning because the planner cannot compare a cast expression against partition bounds; rewrite it as a half-open range on the raw column [3,5]. Third, battle scar three: over-partitioning. When Planning Time dwarfs Execution Time, you have too many partitions - ChartMogul's LIST partition explosion is the canonical example, and the audit trail suggests HASH partitioning with a deliberate partition count instead [1,2]. 💡 Insight: pruning is driven by partition bounds, not by indexes - indexes on the key column are unnecessary; composite indexes on the filter columns are where the real win lives [2,4]. The workflow is simple to internalize: prove pruning, inspect the access path, kill the sort, question the key, then lock in the plan with a regression test [3,5]. Fix the query before you touch the schema - nine times out of ten the schema was never the problem.

## Conclusion

The next time a query on your partitioned table crawls, run EXPLAIN (ANALYZE, BUFFERS) before you resize the instance or sprinkle indexes. Prove pruning happened, inspect the access path inside the surviving partition, hunt down the expensive sort, then question the partition key itself - ChartMogul's 5x speedup came from precisely this discipline when hundreds of LIST partitions became the bottleneck [1]. Convert that plan shape into a regression test on the spot, and tomorrow you will catch the next failure in CI instead of on call. The one insight worth sharing with your team: pruning is not delivered by the DDL, it is earned by every WHERE clause you write [9].
