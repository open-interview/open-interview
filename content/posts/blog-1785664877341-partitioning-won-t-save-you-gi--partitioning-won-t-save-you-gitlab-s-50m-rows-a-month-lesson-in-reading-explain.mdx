## Hook — The 3AM Audit That Kept Timing Out

The audit events controller on GitLab.com is not supposed to be the thing that wakes you up at 3am. But there it is: the page renders, the database churns, and the request dies in a timeout. The table behind it, audit_events, grows by roughly 50 million rows every month [1]. Fifty million. A month. No amount of add-an-index-and-hope is going to paper over that. The team's first move was the sensible one — partition the table by date so each query only touches the slice it needs. And here is the twist: the queries were still slow. Partitioning was the necessary first step, but it turned out to be the easy 20% of the fix. The remaining 80% lives in a place many developers dread opening: the EXPLAIN plan.

## Problem — Why 100 Million Rows Makes Simple Queries Lie

PostgreSQL handles a few million rows gracefully. At 100 million, everything changes. The planner has to choose between a sequential scan — reading every page of every partition — and an index scan that bounces between the index and the heap. When a WHERE clause filters on date and status, the naive assumption is that a B-tree index on each column will save you. It will not: for each row, PostgreSQL must visit index A, then index B, then merge the results, and that bitmap-and dance can be slower than just reading the table [9]. Meanwhile, the ORDER BY you added for the UI silently triggers a sort that spills to disk. The stakes are not academic. A controller that used to answer in 200ms now returns 504s, and every retry from the front end makes the queue worse. This is the moment where most teams do one of two things: add more indexes and hope, or blame the database and scale it up. Both are expensive. There is a third path, and GitLab walked it.

## Real-World Case — GitLab's 50M-Rows-a-Month Wake-Up Call

GitLab.com runs GitLab itself on PostgreSQL, and its fastest-growing tables — web_hook_logs, events, audit_events, and the CI/CD tables — ballooned to hundreds of gigabytes [1]. Audit events alone hit roughly 50 million new rows per month, and the audit events controller began timing out under the load. The team adopted PostgreSQL declarative partitioning, splitting the tables by range on created_at so queries could target a narrow band of recent data [2]. But here is the plot twist: date-range queries stayed slow. Partitioning changes how data is stored and maintained; it does not automatically change how queries are executed. What partitioning did unlock was operational leverage: VACUUM and index maintenance became per-partition operations, old partitions could be dropped instead of running multi-hour DELETEs, and the CI/CD tables gained an emergency partition-detachment escape hatch if performance ever degraded again [1]. The lesson crystallizes into a question every developer should ask: if partitioning alone was not the fix, what actually was? The answer lives in the plan the planner prints for you — if you know how to read it.

## Deep Dive — Reading the Tea Leaves of an EXPLAIN Plan

Building on GitLab's experience, think of EXPLAIN as the planner's confession of its own reasoning. Run it with ANALYZE and BUFFERS, and three things matter. First, partition pruning: the plan should show a small number of scanned partitions, not all of them [4]. If the planner reports visiting every partition, the WHERE clause is fighting the partition key — often because a function or a cast wraps the key column and hides it from the pruning logic. Second, scan type: a Seq Scan on a 100M-row table means the planner decided the index was not worth it, usually because row estimates are skewed or the index cannot cover enough of the WHERE clause [3]. Third, the expensive operators: a Sort or HashAggregate node near the top of the tree is a signal that the query is doing heavy lifting an index could preempt. Here is the counterintuitive part: the order of columns in a composite index matters more than the number of indexes you create. An index on (event_date, status) serves date-range filtering and status filtering in one structure, while two single-column indexes force bitmap-and merges [5][9]. For extra credit, a covering index with INCLUDE pushes selected payload columns into the leaf pages, letting the planner answer the query without ever touching the heap — a classic index-only scan [7]. And when the sort still hurts, clustering the table to match the index order lets the planner read rows already in the right sequence [6]. One more surprise: the partition key itself may be wrong for the query pattern. If the hot path filters on created_at but the business logic thinks in event_date, the pruning math silently collapses. Check the shape of your actual queries — pg_stat_statements is the perfect place to see them ranked by execution time [8].

## Workflow — A Five-Step Diagnosis You Can Run Today

Now that you know what the plan is telling you, here is the step-by-step drill — the same loop GitLab's engineers would recognize. Start by reproducing the slow query with EXPLAIN (ANALYZE, BUFFERS), then answer three questions in order: is pruning happening, is the scan type reasonable, and is there an expensive sort or aggregate? Each answer points to a specific remedy, and after every change you re-run the plan and compare buffer counts before touching anything else. The figure below maps the full flow from slow query to shipping. Take the branches in order — skipping straight to CLUSTER without confirming pruning usually means you optimized the wrong layer. And keep a feedback loop: re-measure p95 latency before and after each step, because the plan can look perfect while the production access pattern still hurts.

## Lessons Learned — Battle Scars and the 10-Minute Audit

After walking this path, the takeaways are sharp. Partitioning is storage surgery, not a query fix — always pair it with a pruning check [2]. Read EXPLAIN for exactly three things: pruning, scan type, and expensive operators [3]. Prefer one composite index on (partition key, filter columns) over several single-column indexes [5]. Add covering indexes with INCLUDE when queries repeatedly fetch the same payload [7]. And build a habit of auditing index usage: pg_stat_user_indexes will show you which indexes have a zero idx_scan count, and every one of those is dead weight costing writes on every insert [10]. If you take nothing else from this story, take this: the fastest query is the one you prove, not the one you assume. GitLab proved their way out of 50 million rows a month, and so can you.

## Conclusion

The moral of GitLab's story is that partitioning buys you a better starting point, not a finished product — the real speed lives in pruning that works, composite indexes that match your WHERE clause, and a sort that never has to happen. Before your next 100M-row table becomes a 3am pager, run the 10-minute audit: one EXPLAIN (ANALYZE, BUFFERS), three questions, five steps. Share this with your team tomorrow — the engineer who reads the plan instead of guessing wins the query every time.
