## Hook — The Team That Deleted Their Build Step (and Shipped Anyway)

Picture a product team staring at a webpack config at 11pm, wondering why a two-line color change requires a 90-second rebuild. Now picture the opposite: a team that ships real-time chat, a publishing platform, and a kanban tool with no bundler at all. That contradiction is the hook here. 37signals announced they were leaning into a no-build, vanilla-CSS approach precisely because the modern frontend toolchain had grown heavier than the problems it solved [1]. They called the bet: the browser itself is now a capable runtime, so treat it as one. The result? A small team replacing both client-side JavaScript and server-side Ruby conditionals with plain stylesheet rules [1]. If a chat app with live updates can do this, your docs page tabs certainly can. But that raises a sharp question: how far can declarative CSS really go before it breaks? The answer is further than most developers assume — and the trade-offs are the interesting part.

## Problem — The JavaScript Tax on Simple Interactions

Every interactive widget carries a hidden tax: script to load, state to hydrate, event listeners to clean up, and accessibility bugs that appear when the JS and the DOM disagree. A tab panel is the canonical example. The naive approach wires `click` handlers to buttons, toggles `aria-selected`, swaps a class, and hopes nothing desynchronizes. Many developers think this is the only path — until they learn that a group of radio inputs already *is* a state machine, and the browser maintains it for free [7]. The problem is not that JavaScript can't do this; it's that JavaScript is the wrong tool for a job the browser already solves declaratively. This matters most for design-system documentation, where tabs are static, content is known at author time, and the only real requirements are layout, motion, and keyboard accessibility. Adding a runtime here means shipping a dependency to display text that never changes. Consequently, the challenge becomes: can you express tab switching, responsive card layout, staggered animation, and visible focus entirely in CSS — and do it without locking out users who prefer reduced motion [4]? The stakes are maintenance cost, bundle size, and a class of bugs that simply stop existing when there is no JavaScript to desynchronize.

## Real-World Case — 37signals (Basecamp)

The most documented modern example of betting on vanilla CSS comes from 37signals. Rather than adopting a framework-and-bundler stack, they shipped three production applications — Campfire (real-time chat), Writebook (publishing), and Fizzy (kanban) — on raw CSS with no preprocessors, no bundler, and no build step [1]. Across those three apps they maintain roughly 14,000 lines of CSS across 105 files, with zero Sass, PostCSS, or Tailwind [1]. The timing was telling: Campfire shipped its first beta one week before Firefox became the last major browser to support `:has()` [1] [8]. That let the team replace JavaScript and server-side conditionals with declarative rules, and they evolved the pattern over releases — adding container queries, then `@starting-style`, then `@layer` and `color-mix()` [1]. The lesson is not that JavaScript is bad; it's that a small team, deliberately choosing the platform, can delete entire categories of tooling and still ship. That same philosophy is exactly what a CSS-only tab panel demands. So how do the mechanics actually work under the hood?

## Deep Dive — Radios, Sibling Selectors, and Motion That Bows Out

The core trick is that radio inputs with a shared `name` attribute form a mutually exclusive group, and the browser guarantees only one is checked at a time [7]. Labels with a matching `for` attribute toggle those inputs, which means you get full keyboard behavior — arrow keys move between options — for free [7]. Now the magic: the `:checked` state of each radio can be targeted with a sibling combinator to reveal or hide an associated panel [3]. Specifically, `input:not(:checked) ~ .panel { display: none; }` hides every panel whose radio isn't selected, and the one that remains visible is the active tab. For layout, CSS Grid gives you `repeat(2, 1fr)` to create a stable 2x2 card arrangement on desktop, collapsing to a single column under a mobile breakpoint [2]. Each card's image area uses `aspect-ratio: 16 / 9`, which reserves the correct box before the image even loads and eliminates the old padding-top percentage hack [6]. Motion is where accessibility discipline shows up. Wrapping the entrance animation in `@media (prefers-reduced-motion: no-preference)` means users who ask for less motion simply get the final state with no fade, no slide [4]. Finally, `:focus-visible` ensures keyboard users see a clear outline while mouse users aren't distracted by it [5]. Here is the thing though: this pattern isn't just tidy, it changes what bugs are even possible.

## Workflow — From Markup to Visible Panel

The flow is deceptively linear, and each step maps to a single declarative concern. The visual story is captured in the diagram below.

1. Author a radio input per tab, all sharing one `name`, with the first marked `checked` so a panel is visible on load [7].
2. Pair each radio with a `` whose `for` points at the input — this is the click and keyboard target [7].
3. Place each panel as a following sibling of its radio inside the same container, so sibling combinators can reach it [3].
4. Hide panels whose radio is not checked using `input:not(:checked) ~ .panel` [3].
5. Lay out the visible panel with Grid: two columns on desktop, one on mobile [2].
6. Reserve each image box with `aspect-ratio: 16 / 9` so the grid never jumps [6].
7. Add a staggered `@keyframes` entrance, gated behind `prefers-reduced-motion: no-preference` [4].
8. Keep `:focus-visible` outlines intact so keyboard navigation remains obvious [5].

Notice that no step requires a runtime. The browser's own state, layout, and media-query engines do the work. This is the 37signals thesis in miniature: push behavior into the platform, and the maintenance surface shrinks [1].

## Lessons Learned — What to Carry Into Tomorrow

The moral of this journey is that declarative CSS is not a downgrade — it's a deliberate trade. You give up imperative flexibility and gain a smaller maintenance surface, fewer hydration bugs, and accessibility that comes from native semantics rather than careful scripting [7]. Here are the battle scars worth remembering:

- ⚠️ Watch out: sibling combinators only reach *later* siblings. If your label or panel is not a following sibling of the input, the pattern silently fails [3].
- 💡 Insight: radio groups already give you arrow-key navigation and mutual exclusivity, so you often don't need any ARIA role rewriting [7].
- 🎯 Key point: fence every animation behind `prefers-reduced-motion: no-preference`; the default should be no motion at all [4].
- 🔥 Hot take: if your tab content is static and known at author time, shipping JavaScript is paying rent on a house the browser already built [1].
- 💡 Insight: `aspect-ratio` replaced an entire generation of padding hacks and reserves layout space before assets load [6].

Start small tomorrow: pick one static interactive widget in your docs and rebuild it with radios and labels. Measure the lines of JavaScript you delete. Then ask what else was only complex because a build step made it feel necessary.

## Conclusion

The biggest insight to take to your team is simple: before you reach for JavaScript, ask whether the browser already models your problem. 37signals proved at production scale that a small team can ship chat, publishing, and kanban apps with no build step and 105 stylesheet files [1]. The CSS-only tab panel is the same idea at a smaller scale — radio inputs as a state machine [7], sibling selectors as conditional rendering [3], Grid as layout [2], aspect-ratio as reserved space [6], and reduced-motion as empathy [4]. So here is the actionable next step: find one static interactive widget in your design system, rebuild it declaratively, and count how much JavaScript and tooling disappears. You will likely discover that the hardest part was never the interaction — it was believing you needed a build pipeline to build it.
