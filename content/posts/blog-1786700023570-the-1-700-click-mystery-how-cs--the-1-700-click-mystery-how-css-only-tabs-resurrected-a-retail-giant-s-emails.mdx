## Hook — The no-JavaScript dare

Imagine the meeting. A product lead slides a design across the table: a documentation page with four product categories, each holding a tidy 2×2 grid of cards. There is one catch, delivered with a smile: 'No JavaScript. The page should work even if a script never loads.' Sound impossible? Many developers hear 'interactive' and reach for a framework before the sentence finishes. But here is the plot twist — the web shipped this feature decades ago, hiding in plain sight inside a form control nobody takes seriously: the radio button. What reads like a trivia question for coding interviews is actually a production pattern used by one of Europe's largest consumer-electronics retailers to turn static email into a storefront that got clicked 1,700% more often [1]. Before the payoff, though, the real pain point deserves a closer look — because the pattern only matters when the problem is genuine.

## Problem — The static page trap

Here is the situation: the design-system docs page renders product categories as plain, stacked blocks. Content is technically there — titles, images, meta lines — but every category competes for the same screen space, pushing the good stuff below the fold. On mobile it is worse: a single column of cards turns what should be a 2×2 grid into a scroll marathon. Meanwhile, email marketers hit the identical wall. Email clients — Gmail, Outlook, Apple Mail — execute JavaScript sparingly, if at all, and many strip `` tags outright [8]. Consequently, every 'interactive' idea dies on arrival unless it is expressed in pure HTML and CSS. The shared requirement across both worlds is deceptively simple: let people switch between groups of content without a page reload, without JavaScript, and without sacrificing keyboard focus or motion preferences. Moreover, this has to survive a 768px viewport. The accessibility angle quietly raises the stakes too — a tab switcher that ignores keyboard users is not just sloppy, it is a compliance risk in many regulated industries [6]. So how does a retailer with a huge, diverse product portfolio — and mobile as a key channel — let recipients explore categories directly inside the inbox? That is exactly the problem MediaMarkt faced.

## Real-World Case — MediaMarkt's inbox storefront

MediaMarkt Saturn, operating under Ceconomy AG, runs one of the largest consumer-electronics retail ecosystems in Europe, and Switzerland was the test bed. Their promotional emails were static — banners and fixed product grids offering little interaction. Recipients could look, but they could not explore. With a massive product portfolio and mobile as a dominant channel, the team needed people to browse product categories directly inside the inbox, without ever clicking through to a landing page [1]. So they rebuilt the email around modular, interactive panels — the same radio-to-panel pattern that powers docs-page tabs, tuned for email-safe markup. The numbers changed everything: a +1,700% increase in clicks compared to static emails, and an 11–12x revenue uplift versus the control group in the proof-of-concept [1]. The modular panel is now reused across seasonal mailings, category spotlights, and personalized recommendation emails [1]. Here is the uncomfortable implication: the difference between a campaign that converts and one that is ignored was not a bigger budget or fancier tooling. It was a CSS trick a junior developer could build in an afternoon. That is the discovery moment — and it leads straight into the mechanics.

## Deep Dive — The radio hack, minus the smoke and mirrors

The entire pattern rests on three pillars. First, the HTML: a set of radio inputs sharing the same `name` attribute, each paired with a `` and a panel. Because radios are mutually exclusive within a name group, exactly one can be `:checked` at any moment [8][2]. Second, the CSS: the general sibling combinator (`~`) styles every sibling that comes after an element — so `.tabs input#tab-overview:checked ~ .panel--overview` reveals precisely the panel belonging to the checked radio [3]. Third, presentation: CSS Grid turns each panel into a 2×2 card layout with `repeat(2, 1fr)`, collapsing to a single column below 768px via a media query [7][10]. The image areas stay perfectly proportional with `aspect-ratio: 16 / 9` — a property that finally makes the 'fixed 16:9 image area' requirement a one-liner instead of the padding-hack sorcery of years past [4]. The entrance animation adds the human touch: a `fadeSlideIn` keyframe with staggered delays on `nth-child` so cards cascade in one after another — but only when the user has not requested reduced motion [5][9]. Now for the plot twist that separates a good answer from a great one: this is not a true ARIA tabs component. The WAI-ARIA tabs pattern expects arrow-key navigation and `role=tab` semantics, which pure CSS cannot fully deliver because focus management requires scripting. Treat this as a display switcher — perfect for product carousels, docs pages, and accordion-style toggles — but reach for a JavaScript component when screen-reader tab semantics are non-negotiable. Moreover, there is a hidden trap in the ordering: the `~` combinator only reaches siblings that come *after* the input in the DOM. If a panel sits before its radio, the selector silently matches nothing and the tab looks broken for reasons that make no sense — a classic battle scar. ## Workflow — From requirement to shipped component

Building on those mechanics, here is the build order that turns the requirement into a component that survives code review. Figure 1 below shows the whole decision flow at a glance. First, mark up the skeleton: radios, labels, and panels in DOM order, with each radio's `id` matching its label's `for` attribute [8]. Second, set one radio `checked` so a panel is visible on load — otherwise every panel hides and the page looks empty. Third, write the show/hide rules with the sibling combinator, one selector per panel [3]. Fourth, layer the grid: `repeat(2, 1fr)` on desktop, `1fr` on mobile, with `gap` for breathing room [7][10]. Fifth, fix the image areas with `aspect-ratio: 16 / 9` and add the staggered entrance animation guarded by `prefers-reduced-motion: no-preference` [4][5]. Finally, add a `:focus-visible` outline so keyboard users see exactly where they are [6]. Then run a keyboard walkthrough, a 375px viewport pass, and a screen-reader pass — and the component is done.

Also note the fallback philosophy: if JavaScript were ever added to this page later, nothing here breaks; the CSS merely becomes progressive enhancement.

## Lessons Learned — What this pattern teaches beyond CSS

Step back and the real lesson is not about selectors — it is about constraints. MediaMarkt did not earn +1,700% more clicks by adding technology; they earned it by removing technology until only the essential interaction remained [1]. Here are the takeaways that survive the demo:
- Constraint is a creativity multiplier. Banning JavaScript forced the team into the radio hack, which turned out faster, lighter, and email-safe [1].
- Accessibility is a feature, not a checkbox. `focus-visible` outlines and `prefers-reduced-motion` are what make the pattern acceptable to ship — not optional polish [5][6].
- Know your selector's limits. The `~` combinator only looks forward in the DOM; order your inputs before their panels or nothing matches [3].
- Match the semantics to the stakes. CSS-only tabs are a display switcher; when true tab roles and arrow keys matter, choose a real component.
- Mobile is not a smaller desktop. The 2×2 grid and the single-column collapse are two separate designs, united by one media query [10].

💡 Insight: An element set to `display: none` does not participate in layout, so toggling it back on re-triggers its animation — which is exactly why switching tabs replays the stagger instead of freezing it [9].

⚠️ Watch Out: Forgetting the `checked` attribute on one radio produces an empty-looking page on first load, and hiding radios with `position: absolute` and `opacity: 0` (rather than `display: none`) keeps them focusable for keyboard users — an easy accessibility win.

🔥 Hot Take: 'Pure CSS tabs are a hack' is an opinion, not a fact. MediaMarkt's 11–12x revenue uplift suggests the market does not care how 'interactive' it feels — only that it does [1].

🎯 Key Point: Tomorrow, take one static page in your product and rebuild its content switcher with this pattern. No dependencies, no build step, no runtime cost — just a few inputs and a better click-through.

## Conclusion

The journey started in an inbox that nobody could touch and ended with a component so reusable that a retailer keeps shipping it across seasonal mailings and personalized recommendations [1]. The moral: the best frontend solutions are not the ones with the most features — they are the ones that survive the harshest environments. CSS-only tabs weigh zero bytes, break under no circumstances, and respect every user's motion and focus needs. So tomorrow, take one static section of your design-system docs and give it the radio treatment. The interaction may be small, but the click-through can be enormous — and that is the one insight worth sharing with your team: sometimes the most powerful interactivity is the kind nobody had to write.
