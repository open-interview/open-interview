Policybazaar, India's largest insurance marketplace, discovered this the hard way when its plan-comparison tool and health-quiz flows quietly accumulated event listeners, class toggling, and selection-validation code that could drift out of sync at the worst possible moment — right when a user was about to buy. So the team made a bold call: delete the JavaScript and let CSS carry the interaction [1]. This is the story of how a humble radio button replaced an entire layer of logic, and how you can ship the same CSS-only tab panels in your own design-system docs.

## Hook — The state you need already exists in the browser

Here is the plot twist that saves this story: the state you need for a tab panel has been hiding in every browser since 1995. It lives inside a `` element, patiently waiting to be useful. The moment you realize a checked radio carries real, queryable state — via the `:checked` pseudo-class — a whole category of JavaScript starts to feel optional. This is not a demo trick for CodePen. This is a production architecture decision made on a platform with tens of millions of monthly users [1]. Before any selector is written, that's the mindset shift: the browser already solved tab switching, one toggle at a time. Developers just forgot where the switch lived.

## Problem — Tab panels feel harmless, until they live on a critical path

Tab panels look innocent. A few buttons, a little conditional rendering — what could possibly go wrong? Plenty, once you stack them into a journey users depend on. JavaScript-driven tabs mean event listeners attached at mount, class names toggled in exactly the right order, and application state that must stay in sync with the DOM on every render. Add React or a hydration step and you get a whole new failure mode: a flash of the wrong panel before the JavaScript catches up. On a health-quiz or plan-comparison flow, that isn't an annoyance. A desync can make a user's selections appear wrong at the precise moment they're deciding what to buy. Every listener adds bytes to a page the business wants to load in milliseconds, and every class toggle is another place where two versions of the truth can disagree. Consequently, the cost compounds: more JavaScript, more edge cases, more test suites, and more ways for a well-intentioned quick fix to quietly break a flow that was already working fine.

## Real-World Case — Policybazaar removes the JavaScript layer

Policybazaar hit this wall in two of its most trafficked flows [1]. The plan-comparison tool needed to validate which plan types could be selected together, while the health quiz used event listeners to detect answered questions and animate the transition to the next one. Both relied on JavaScript: validation logic, listeners, class toggling — code that could desync and added real weight to journeys the business could not afford to slow down. Tech Lead Aman Soni reported the fix: eliminate the JavaScript-based selection validation entirely and replace it with a pure CSS solution that reproduces the exact same experience [1]. It shipped to production on a platform serving tens of millions of users. And this pattern scales beyond one company — related HTML-state work at Tokopedia cut up to 70% of a component's React lines of code [1]. The lesson isn't "CSS is a React killer." It's that state the browser already manages is state you never have to manage yourself. JavaScript is great — but using it to reinvent an input's built-in behavior is expensive theater.

## Deep Dive — The radio-to-tab pattern, dissected

The trick is three moving parts that each do one job [4]. First, radios sharing a `name` attribute form a group where exactly one can be `:checked` at any time — a free, browser-enforced state machine. Second, `` elements with a `for` attribute let users flip that state with a click, no `addEventListener` anywhere. Third, CSS sibling selectors read that state and control visibility: `input:checked ~ .panel` renders a panel only when its own radio is active. Here is where many developers stumble, and it's a genuine battle scar. The tempting shorthand `input:not(:checked) ~ .panel` looks elegant but leaks: when several panels follow several radios, one unchecked radio hides panels that belong to other tabs. Scoping the selector inside each tab wrapper — or targeting panels by ID — closes the leak. For the layout itself, CSS Grid with `repeat(2, 1fr)` delivers the 2x2 desktop grid, while a `max-width: 768px` media query collapses it to a single column [2][11]. `aspect-ratio: 16 / 9` locks the image area to a fixed 16:9 without a single JavaScript resize handler [3]. Then come the two accessibility pillars. `prefers-reduced-motion: no-preference` gates the staggered entrance animation so motion-sensitive users get an instant render [6], and `:focus-visible` guarantees a keyboard outline only when focus arrives via keys [5]. You might think hiding the radio breaks keyboard navigation — it doesn't. Keep it in the tab order and the whole panel is fully operable with arrow keys. That's the counterintuitive insight: the more state you hand back to the browser, the more accessibility you get for free.

## Workflow — From requirement to zero-JavaScript tab system

The implementation follows a clean progression, and the Mermaid diagram below maps the decision path. First, structure the HTML so every tab wraps its own radio, label, and panel — keeping the sibling selector scoped. Second, hide all panels by default with `display: none`. Third, reveal only the panel that follows a checked radio. Fourth, layer the grid: two columns on desktop, one on mobile. Fifth, add `aspect-ratio: 16 / 9` to the image containers. Sixth, wrap the entrance animation in a reduced-motion guard and give the cards staggered delays. Each step has one job, and none of them requires JavaScript. The diagram tells the visual story: a single `:checked` state fans out to the grid, the animation, and the focus behavior.

## Code Example — The full CSS-only tab panel, line by line

Below is the production-shaped implementation. The HTML keeps each radio, label, and panel inside its own `.tab` wrapper, which scopes the sibling selector and prevents the cross-tab leak described earlier. The CSS uses `display: contents` so the labels form a single row of tab buttons while the panels drop to their own full-width rows. The radio stays in the document flow for keyboard users but is visually hidden, and `input:focus-visible + label` maps the keyboard ring onto the visible label. The staggered animation only runs when the user has not requested reduced motion, and the 16:9 image area holds its shape no matter what's loaded inside it.

## Lessons Learned — What this pattern changes about your defaults

The takeaways that stick: start from existing browser state before reaching for a state library. A radio's `:checked` status is state management, free of charge and immune to desync. Scope your sibling selectors — `input:checked ~ .panel` inside a wrapper beats `input:not(:checked) ~ .panel` in the global DOM, every time. Treat `aspect-ratio` and Grid as layout utilities that replace whole categories of resize-handler JavaScript [2][3]. Gate every animation behind `prefers-reduced-motion` and let `:focus-visible` handle outlines, and the feature is accessible by construction rather than by retrofit [5][6]. The real-world proof is already in production: Policybazaar runs these patterns on journeys with tens of millions of users [1]. The next time a tab panel, an accordion, or a quiz appears in your design system, ask one question first: what state does the browser already hold that you're about to duplicate?

## Conclusion

The pattern Policybazaar shipped to tens of millions of users is the same one you can adopt tomorrow [1]. Before you scaffold another component with a state library and a handful of event listeners, ask what the browser already tracks for free — a radio's checked state, a grid's column count, a user's motion preference. Hand that state back to CSS and you lose the desync risk, the bundle weight, and a whole class of bugs in one move. The memorable insight to share with your team: the best state management is the state you never wrote.
