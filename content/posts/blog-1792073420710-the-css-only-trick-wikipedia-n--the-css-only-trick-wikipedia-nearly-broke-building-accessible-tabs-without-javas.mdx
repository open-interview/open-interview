In May 2020, the Wikimedia Foundation discovered that its beloved CSS checkbox hack — the same hidden-input-plus-`:checked`-selector pattern used to build JavaScript-free tabs — was silently breaking Wikipedia's accessibility. Screen reader users heard "checkbox" instead of "button" on the site's most-used menus, and the resulting bug, T253650, took roughly 16 months and three patch attempts to fix in production [1]. That saga is a cautionary tale every frontend developer should internalize before reaching for the CSS-only tab trick — a pattern that is genuinely powerful, but only when you pair it with the right accessibility and motion-sensitivity safeguards.

---

> ### Real-World Case — Wikimedia Foundation
>
> To cut JavaScript and keep Wikipedia's header menus working without JS, Wikimedia's Vector skin used the CSS checkbox hack — hidden `input[type=checkbox]` + `:checked` + sibling selectors — the exact same state pattern family as CSS-only radio tabs. Screen reader users then found the 'More' and 'User menu' dropdowns on Wikipedia announced as 'checkbox' instead of 'button', with no expanded/collapsed state.
>
> | | |
> |---|---|
> | **Challenge** | The CSS-only pattern conveyed the wrong role and state to assistive technology, failing expectations for WCAG Name/Role/Value: screen readers (tested with Narrator, NVDA, JAWS, VoiceOver) said 'checkbox' when opening Wikipedia's main menus, and `aria-expanded` could not be set without JavaScript because the state lived purely in CSS. |
> | **Solution** | Wikimedia first tried keeping the hack and spoofing `aria-expanded` purely in CSS using visually-hidden label text ('expanded'/'collapsed') per the Inclusive Components pattern (Gerrit 715617, merged Sept 2021), plus `role=button` on the checkbox and `aria-hidden` on the label to cut verbose double announcements. They later standardized it into a shared `checkboxHack.js` utility that syncs `aria-expanded` when JS is available, and filed T333394 to replace the hack entirely with native `/` — only to stall because of serious Chrome crashes when `details` is used. |
> | **Outcome** | Bug T253650 (filed May 2020) was verified fixed in Wikipedia production in September 2021 after ~16 months and multiple patch attempts (Gerrit 598801 abandoned, 715617 and 721399 merged), with QA confirming menus now announce as buttons for logged-in and logged-out users. The pattern spawned a full accessibility audit (T243126), a shared library, and eventually a migration plan away from the hack. |
> | **Lesson** | A CSS-only `:checked` toggle works perfectly for sighted mouse users but silently misreports role and state to assistive tech — the 'zero JS' win can become a production accessibility bug on one of the world's largest sites, and the pure-CSS fixes get hacky fast (spoofing ARIA text with generated content), so plan for progressive enhancement with JS from day one. |

## Lessons Learned — What to Ship Tomorrow, and What to Avoid

The journey from Wikimedia's 16-month bug to a clean CSS-only tab panel reveals a handful of transferable truths. First, CSS state hacks are legitimate — but semantics travel deeper than styling, so always verify what a screen reader actually announces, not just what the browser renders [1]. Second, motion should be opt-in via `prefers-reduced-motion: no-preference`, not patched afterward with a `reduce` override [4]. Third, modern layout primitives do more heavy lifting than you remember: `aspect-ratio` replaces brittle padding hacks [5], and one Grid declaration handles your responsive card layout [3]. Here is what you need to know before your next docs page ships:

- Radio + shared `name` = a zero-byte, browser-enforced state machine [2]
- The `~` combinator only works on same-level siblings — flat DOM or broken tabs
- `aspect-ratio: 16/9` is one line versus ~15 lines of padding-top math [5]
- Wrap animations in `prefers-reduced-motion: no-preference` [4]
- `:focus-visible` gives keyboard outlines without mouse-click outlines [4]
- If audited, layer `role="tablist"`/`role="tab"`/`role="tabpanel"` onto the markup [6]

Battle scars worth remembering: a common mistake is nesting panels inside a wrapper, which silently breaks the sibling selector; another is assuming `aria-hidden` fixes semantics when it actually hides content entirely. After debugging this pattern many times, the pro tip is this — test with a real screen reader (VoiceOver or NVDA) before declaring victory, because the browser's devtools will happily tell you the CSS is correct while the announcement is wrong [1]. The moral of the story: CSS-only interactivity is not about avoiding JavaScript as a ideology — it is about choosing the smallest tool that is also semantically honest. Build your tabs with radio inputs, respect reduced motion, keep focus visible, and audit what assistive technology hears. Do that, and you get Wikipedia's performance win without Wikipedia's 16-month accessibility bill.

## Conclusion

The path from Wikimedia's 16-month accessibility bug to a working CSS-only tab panel is really one continuous lesson: clever CSS state tricks buy you zero-JavaScript interactivity, but only honest semantics, opt-in motion, and visible keyboard focus make them shippable. Tomorrow, flatten your tab DOM so sibling selectors actually match, wrap every entrance animation in `prefers-reduced-motion: no-preference`, and run your component through a real screen reader before calling it done. The one insight worth sharing with your team: you cannot style your way out of a semantic gap — verify what assistive technology announces, not just what the browser renders.
